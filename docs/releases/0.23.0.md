You can now move a coding agent's old builds to the Trash, one by one: Claude Code's and Cursor's agent's, on macOS and Linux. 0.22.4 and 0.22.5 were not released on their own; this release carries them.

> **DeepDriveCleaner deletes files.** It can remove almost anything it is told to, by you or by an agent acting for you. Use it at your own risk: nobody who made it is responsible for what it removes. Read [DISCLAIMER.md](https://github.com/SmartAndPoint/DeepDriveCleaner/blob/v0.23.0/DISCLAIMER.md).

- **Old agent builds.** Claude Code keeps each build it installs as a file in `~/.local/share/claude/versions`, and Cursor's agent as a folder in `~/.local/share/cursor-agent/versions`. The scan now lists these two folders under "Coding agents", class `review`, and each build in them as an entry. In the app's Review window you pick old builds one by one ("N old builds"); `ddc clean --items` takes them from a list. They go to the Trash only: `--yes` never selects one, and `--permanent` refuses it. A build does not come back by itself; `claude install <version>` fetches one again.
- **What stays locked.** A build is locked `build-in-use` when the `claude` (or Cursor's `agent`) launcher points to it, a process of yours runs it, Claude Code's own lock file names a live process, or it is the newest build. Every build of a harness is locked `builds-unknown` when ddc cannot tell: no launcher or a custom one, a process of yours named as the harness that ddc cannot read, a process of another user with that name, a hidden process table (Linux `hidepid`), or a home on a network file system. The locks are read at the scan, at the dry run and again right before the move.
- **Few on most Macs.** Claude Code already deletes its own old builds and keeps the ones in use plus two more, so expect one or two (about 0.25 GB each). Cursor's agent documents no such cleanup.
- **The app** shows the builds folders as builds, not as sessions, and names each lock.
- **macOS: in use through a link (0.22.4).** Before a clean, ddc checks that no process of yours runs a program inside the item. On macOS it looked only at the path a process was started by. A program started through a symlink, say a venv's `python` that points into a pyenv version, or `/opt/homebrew/bin/x` that points into its Homebrew keg, was not seen in the folder it really runs from. Now the check also reads the resolved file, as it already did on Linux. So you may see more items skipped as "in use" while such a program runs.
- **macOS: another user's process has a start time (0.22.4).** ddc can now tell when another user's process started, so a process of another user is no longer read as "no process".
- **Groundwork (0.22.4):** ddc can read the names of other users' processes, tell whether `/proc` hides other users' processes (`hidepid`), and tell whether the home is on a network file system. Nothing uses them yet.
- **Native test runs never keep a stale binary (0.22.5).** `scripts/native-windows.sh` and `scripts/native-linux.sh` copy the source tree to a Windows or Linux machine and test it there. They kept each file's own time, so a tree copied after another one could look older than the last build, and cargo kept the old binary: once, four tests failed on a command the copied tree had. Now every file gets the time of the copy.

**Report schemas.** The scan report moves to schema 6, the clean report and the journal to 9, the progress events to 7, for the new locks and the origin kind `builds`. Update the app and the CLI together: an older app shows a report of the new version as one it cannot read.

**Upgrading.** `brew upgrade --cask deepdrivecleaner`, the app's Check Now, the install script, or the zip below.
