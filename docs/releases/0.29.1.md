A Windows step on the way to Windows support: ddc now also sees a program that runs code from inside a folder. Windows is still not supported, so nothing of this runs outside the tests yet. On macOS and Linux nothing changes. 0.29.0 was not released on its own; this release carries it: on Linux, ZFS child datasets inside a scan root are now counted, and their snapshots never are.

> **DeepDriveCleaner deletes files.** It can remove almost anything it is told to, by you or by an agent acting for you. Use it at your own risk: nobody who made it is responsible for what it removes. Read [DISCLAIMER.md](https://github.com/SmartAndPoint/DeepDriveCleaner/blob/v0.29.1/DISCLAIMER.md).

- **Windows: a loaded module counts as in use.** On Windows a folder can be renamed while a program has a DLL, a `.pyd` or a `.node` file from it loaded, and deleting it then fails half way. Before a permanent delete, ddc now reads the modules each of your processes has loaded, and skips an item that holds one as "in use". A module counts both by the name it was loaded by and by the file it really is. So a module loaded through a junction from a store outside the item (pnpm does this) is seen too.
- **Partly read is still counted.** If ddc cannot read a module's name, it leaves that one out, counts the process as read only in part, and still checks the others.
- A move to the Recycle Bin does not look at loaded modules. It is a rename, which Windows allows with a module loaded, so the item moves with the program still running, as the Trash does on macOS.

- **Linux: ZFS child datasets are counted (0.29.0).** On a ZFS home (Ubuntu's ZFS install, Proxmox) a dataset below the scan root is its own mount, so the scan stopped there as at another filesystem. ddc now enters a child dataset of the same pool when it is mounted where it inherits its mount point: `pool/home/you/work` at `~/work`. A dataset with its own `mountpoint=` elsewhere, and a bind mount of a dataset, stay another filesystem. Each dataset is read beneath its own anchor, so nothing outside it is crossed.
- **`.zfs` is never entered (0.29.0).** The hidden snapshot folder at a dataset's root is listed as `snapshot`, never counted, and the scan never mounts a snapshot by looking into it.
- **A dataset is never removed (0.29.0).** A finding that holds a dataset, or is one, is listed as `holds-subvolume` and not planned, as for btrfs subvolumes. An item inside a dataset is cleaned as usual; its move to the Trash goes into that dataset's own `.Trash-<uid>`.
- **A ZFS clone (0.29.0)** is an ordinary dataset and is counted in full, though it shares blocks with the snapshot it came from.
- **`ddc du` (0.29.0)** now counts child datasets below a root, which `du -x` does not.

**Report schemas.** None change.

**Upgrading.** `brew upgrade --cask deepdrivecleaner`, the app's Check Now, the install script, or the zip below.
