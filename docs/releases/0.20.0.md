On Linux, the Trash is now ddc's own: an item moves to a Trash on its own filesystem, or it is skipped, and nothing is ever copied. `ddc` also removes a coding agent's dead worktree through git (0.19.0). 0.18.1 to 0.19.1 were not released on their own; this release carries them.

> **DeepDriveCleaner deletes files.** It can remove almost anything it is told to, by you or by an agent acting for you. Use it at your own risk: nobody who made it is responsible for what it removes. Read [DISCLAIMER.md](https://github.com/SmartAndPoint/DeepDriveCleaner/blob/v0.20.0/DISCLAIMER.md).

- **Linux: the move to the Trash.** Before, ddc used a library that moved an item by path and, when the item was on another filesystem, copied it into the home Trash and deleted the source. Copying can fill the home disk, and it reads whatever is there. Now ddc moves the item itself, from the folder it checked, with one rename:
  - into the home Trash (`~/.local/share/Trash`, or `$XDG_DATA_HOME/Trash`) when the item is on the same mount and device;
  - otherwise into the Trash at the top of the item's own mount: `.Trash/<uid>` if you made it there, else `.Trash-<uid>`, made with mode 0700. One the user owns with looser bits is set to 0700 first.
  - The `.trashinfo` file is written first, so a file manager can restore the item. After the move, ddc checks that what arrived is the item it checked; if not, it moves it back.
- **When there is no usable Trash**, the item is skipped with the new reason `trash-crosses-filesystem`, and the message says that `--permanent` removes it instead. That happens on a mount whose top you cannot write and that holds no Trash of yours, and in a btrfs subvolume other than the Trash's. `ddc clean --items <file> --dry-run` predicts the same skip, and creates nothing.
- **NFS** works: where the server refuses the no-replace rename flag, ddc checks the name and renames.
- **The journal** records where each item went: the Trash folder and the item's name in it.
- Nothing changes on macOS.
- **Dead agent worktrees are selected (0.19.0).** A Claude Code worktree that passes the six conditions of 0.18.0 is `rebuildable` and selected, and counts in the "can free" totals. `ddc clean --yes --class rebuildable` removes it with `git -C <main checkout> worktree remove <path>`. Its branch is kept: `git branch -d` drops it when you want.
- **Only git removes a worktree (0.19.0).** No `--force`, no `git worktree prune`, never a plain delete or a move to the Trash. Before the command, the clean asks git to list the main checkout's worktrees and finds this one by its file identity, not by how its path is spelled. If git does not list it, nothing runs and the item is skipped as "no git lists this folder". Another worktree's administrative folder is never touched, even when that worktree was moved away.
- **The conditions are checked again at the clean (0.19.0).** Between the scan and the clean a worktree can be locked, used, get an initialized submodule, an edit, an ignored file of its own or a new commit. Then it is skipped with the new reason `worktree-kept`, which names the condition and why. A git that fails or hangs keeps the worktree too.
- **Your own worktrees, by list (0.19.0).** A worktree you made yourself (`git worktree add`), or one used an hour ago, is never selected. When you list it (`clean --items`, the app's sheet) or confirm it in the terminal, it is removed. Doing that waives "made by an agent" and "idle", never the rest: a listed worktree with uncommitted work, unique ignored files, an initialized submodule or a commit only it holds is refused as `worktree-kept`, in the dry run already.
- **An exclusion inside a worktree keeps it (0.19.0).** As for any finding, an `--exclude` or a settings exclusion below a worktree protects the whole worktree, since `git worktree remove` would take the excluded folder with it.
- **What is inside goes with it (0.19.0).** A `.venv` or `node_modules` inside a selected worktree is not removed twice: the plan leaves it out and the worktree counts its bytes once. Listing a worktree and something inside it skips the inner item as `inside-another-item`.
- **An orphan worktree** (its repository is gone) goes to the Trash when you list it, or is deleted with `--permanent`.
- **Linux: the clean stays on the scanned mount (0.18.1).** Before it moves or removes anything, the clean opens the item's folder relative to the scan root with `openat2`. A bind mount, any other mount, or a symlink on the way is refused as `parent-changed`; a mount at the item itself is `incomplete`; a scan root renamed away and replaced during a clean is refused. Kernels without the mount id in `statx` read it from `/proc/self/fdinfo`; where no mount id can be read at all, the clean refuses.
- **A FIFO no longer hangs a scan (0.18.2, macOS, Linux).** The few small files the scan reads (a venv's `pyvenv.cfg`, a worktree's `.git` file, `CMakeCache.txt`) are opened without blocking and read up to 4 MiB; a FIFO with that name reads as nothing.
- **Windows (0.18.2).** Those reads never download a OneDrive-style placeholder and refuse a link. Each file with allocated bytes gets its real hard-link count, so a file whose other link lies outside the scan counts as shared, not freed.
- **Windows: cloud placeholders (0.19.1).** A OneDrive-style file that is only in the cloud, or a folder whose contents are not all local, carries the same dataless mark as an evicted file on macOS. The scan skips such a folder as `dataless` and never lists it, since a listing would make the provider download its entries, and a clean refuses such an item, since deleting a placeholder deletes the file in the cloud too. A file moved off by hierarchical storage (`OFFLINE`) is treated the same way.
- Windows is still unsupported: `ddc` there runs only `--version`, `--help` and `rules`.

**Report schemas.** The clean report moves to schema 8, the journal to 8 and the progress events to 6, with the new skip reasons `worktree-kept` (0.19.0, which was 7) and `trash-crosses-filesystem`. Update the app and the CLI together: an older app shows a report of the new version as one it cannot read.

**Upgrading.** `brew upgrade --cask deepdrivecleaner`, the app's Check Now, the install script, or the zip below.
