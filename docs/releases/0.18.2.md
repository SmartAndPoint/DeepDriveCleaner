On Linux a clean now stays on the scanned mount, a scan never hangs on a pipe where a small file should be, and the Windows port reads real hard-link counts. 0.18.1 was not released on its own; this release carries it.

> **DeepDriveCleaner deletes files.** It can remove almost anything it is told to, by you or by an agent acting for you. Use it at your own risk: nobody who made it is responsible for what it removes. Read [DISCLAIMER.md](https://github.com/SmartAndPoint/DeepDriveCleaner/blob/v0.18.2/DISCLAIMER.md).

- **Linux: the clean stays on the scanned mount (0.18.1).** Before it moves or removes anything, the clean opens the item's folder relative to the scan root with `openat2`, the way the scan reads it since 0.17.0. A bind mount, any other mount, or a symlink on the way is refused as `parent-changed`. Before, the folder opened by path, and a bind mount of the same filesystem made after the scan passed every identity check, because both sides have the same inode.
- **A mount at the item itself** is `incomplete`: what is there is not what the scan walked. The dry run says the same.
- **A scan root renamed away and replaced during a clean** is refused too: the clean holds the root it started with.
- **Kernels without the mount id in `statx`** (below 5.8, or a container whose seccomp profile refuses `statx`): the mount id now comes from `/proc/self/fdinfo`, so the scan and the clean still see the mount. Where no mount id can be read at all, the clean refuses, and the scan reads on with the device number as before.
- CI tests this on a real bind mount: a stale plan into the bind mount is refused and nothing moves.
- **A FIFO no longer hangs a scan (macOS, Linux).** The scan reads a few small files it finds, such as a venv's `pyvenv.cfg`, a worktree's `.git` file or `CMakeCache.txt`. A FIFO with that name, or a symlink to one, made the scan wait forever. Now every such read opens without blocking and reads at most 4 MiB; a FIFO reads as nothing.
- **Windows: a cloud file is never downloaded by a read.** The same reads pass the flag that keeps a OneDrive-style placeholder in the cloud, and refuse a link, which on Windows can point to another machine's share.
- **Windows: real hard-link counts.** Each file with allocated bytes gets its link count from one lookup by name. A file whose other link lies outside the scan, such as a uv venv's files linked from the uv cache, counts as shared, not freed, in the full scan and in the check before a clean alike. A count that cannot be read counts as shared too.
- Windows is still unsupported: `ddc` there runs only `--version`, `--help` and `rules`.

**Upgrading.** `brew upgrade --cask deepdrivecleaner`, the app's Check Now, the install script, or the zip below. No report schema changed.
