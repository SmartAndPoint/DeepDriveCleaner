On Linux, a clean now opens each item's folder beneath its scan root, so a mount made inside the root after the scan is refused, not crossed.

> **DeepDriveCleaner deletes files.** It can remove almost anything it is told to, by you or by an agent acting for you. Use it at your own risk: nobody who made it is responsible for what it removes. Read [DISCLAIMER.md](https://github.com/SmartAndPoint/DeepDriveCleaner/blob/v0.18.1/DISCLAIMER.md).

- **Linux: the clean stays on the scanned mount.** Before it moves or removes anything, the clean opens the item's folder relative to the scan root with `openat2`, the way the scan reads it since 0.17.0. A bind mount, any other mount, or a symlink on the way is refused as `parent-changed`. Before, the folder opened by path, and a bind mount of the same filesystem made after the scan passed every identity check, because both sides have the same inode.
- **A mount at the item itself** is `incomplete`: what is there is not what the scan walked. The dry run says the same.
- **A scan root renamed away and replaced during a clean** is refused too: the clean holds the root it started with.
- **Kernels without the mount id in `statx`** (below 5.8, or a container whose seccomp profile refuses `statx`): the mount id now comes from `/proc/self/fdinfo`, so the scan and the clean still see the mount. Where no mount id can be read at all, the clean refuses, and the scan reads on with the device number as before.
- Nothing changes on macOS or Windows. Inside, the Trash port now takes the item's verified folder and name; that is for the next step, ddc's own Trash on Linux.
- CI tests this on a real bind mount: a stale plan into the bind mount is refused and nothing moves.

**Upgrading.** `brew upgrade --cask deepdrivecleaner`, the app's Check Now, the install script, or the zip below. No report schema changed.
