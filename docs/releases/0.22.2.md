`ddc agent status` now runs on Linux, a clean never deletes a folder or a picked file that moved to the cloud after the plan, and on Windows a path read from a file never leads to another machine. 0.22.0 and 0.22.1 were not released on their own; this release carries them.

> **DeepDriveCleaner deletes files.** It can remove almost anything it is told to, by you or by an agent acting for you. Use it at your own risk: nobody who made it is responsible for what it removes. Read [DISCLAIMER.md](https://github.com/SmartAndPoint/DeepDriveCleaner/blob/v0.22.2/DISCLAIMER.md).

- **Linux: `ddc agent status`.** Claude Code, Codex, Cursor's agent and opencode, with their folders and sizes, each session's footprint, and which sessions are live. Before, it refused on Linux with exit 69. The folders are resolved per OS: on Linux, Codex's runtimes are found under the XDG cache, and the Claude desktop app's macOS-only folder is not listed.
- **Linux: a native Claude Code session is recognised.** Its process runs a build in `~/.local/share/claude/versions`, so it is named after the build's version, not `claude`. ddc now tells it by that folder.
- **A session record is read for its own OS.** Claude Code writes the OS in each record (`darwin`, `linux`). Before, ddc took only `darwin` as local, so every Linux record read as unknown.
- **Linux: a session ddc cannot see is unknown, not ended.** A container or WSL may run a Claude Code session whose process this machine does not see, or whose pid belongs to another process here. A record changed in the last 10 minutes that ddc cannot show to be live is now `unknown`, which keeps its transcripts from a clean. An older one reads as ended, as before.
- **macOS:** the same report as before. A process started directly from a build in `versions` now counts as Claude Code's CLI.
- The agent guidance (`SKILL.md`, the `AGENTS.md` snippet) and the README say `ddc agent status` runs on macOS and Linux.
- **0.22.1: a finding evicted to the cloud after the plan is skipped (every OS).** Between the scan and the clean, a sync client can turn a folder into a cloud placeholder. Before, the clean renamed it and deleted it: deleting it first makes the provider download it, and deleting it deletes it in the cloud too. On macOS the process's dataless policy refused the download, but the folder had already been renamed. Now such a finding is skipped as `incomplete`, as the dry run says too, and the last check right before the rename refuses one as well.
- **A picked file or folder evicted after the plan is never moved to the Trash.** It is skipped as `not-an-entry`, as the dry run says.
- **Windows: a path read from a file never leads to another machine (0.22.2).** A worktree's `.git` file, its `commondir` and its back-reference, and a `CMakeCache.txt` name other paths. On Windows such a path can be a share on another machine: opening it connects there, offers your credentials, and can hold the scan for the network's timeout when the host is down. Now a share, a device path or a drive Windows calls remote (`net use`, a `subst` of a share) is not followed, checked where the path is read and again once resolved, since a local symlink can lead to a share. A drive letter with nothing behind it still counts, so a worktree on an unplugged disk is still an orphan. Resolving a path on Windows never downloads a cloud folder.
- Windows is still unsupported: `ddc` there runs only `--version`, `--help` and `rules`. The Windows tests of this run, a folder and a file made `OFFLINE` after the plan, wait for it.

**Upgrading.** `brew upgrade --cask deepdrivecleaner`, the app's Check Now, the install script, or the zip below. No report schema changed.
